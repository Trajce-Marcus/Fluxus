## 1. Entity model (GLOSSARY: org / solution / operation)

- **Solution** = design artifact, the container: SDM config + pages + role defs + **default menu** (M10 — amends "no menus"). No data, users, assignments.
- **Operation** = runtime unit; **links to exactly one solution** (`solution_id` NOT NULL FK). Owns record partition, users, role assignments, files, **operation config** (menu *override* since M10 + future runtime settings).
- Two operations on one solution ⇒ disjoint data/people/menus, shared model + pages.
- Opaque `scope` string splits: design artifacts key on **solutionId**; records + operation config key on **operationId** (endorsed rename of unendorsed "scope").
- **Org** = the tenant everything hangs under (§1a). Single implicit org still (`'default'`); M14 gives it a real row + settings surface, but not signup.

## 1a. Org tier (M14)

The onboarding story, and the shape it implies:

- **A new org starts empty** — zero solutions, zero operations. Console's Solutions list is that empty state, not an error.
- **Two ways to get a solution**: author one in Console (`origin: 'authored'`), or import/buy one from the Catalogue (`origin: 'installed'` + `origin_ref` lineage). The M12 provenance columns are the seam; the import path itself does not exist yet.
- **Then link an operation to it** — that is what turns a design artifact into something running, with data and people.
- **The operation → solution link is binding and permanent** (ruled 2026-07-27). An operation is never re-pointed at another solution: its record partition, role assignments and menu override are all written against that solution's model, so re-linking would orphan every one of them. **Enforced by absence** — there is no update path in the router, the host or the client, and none may be added. Documented on the column.
- **The org is a real thing, not a nameless workspace** — GitHub's model. It has a profile (name, contact email), a registration date and a **plan** (what it is subscribed to; billing itself is later). Console gets an **Organisation** item at workspace level, above Solutions, with a **Profile** form and a read-only **Plan** section; the org name is pinned in the Console header at both IA levels.
- **Not built: signup.** Creating an org from nothing needs the auth tier to resolve user → org, which it does not do. So `orgs.get`/`putProfile` operate on the existing row; there is no `orgs.create`, and `plan`/`status` are ours to set, never the org's — they are not writable through the API.

## 2. Storage (existing Drizzle/Neon pipeline — no new mechanisms)

- `orgs(id, name, contact_email, plan, status, created_at)` — the tenant (M13 name, M14 profile). `operations.org_id` / `user_roles.org_id` have carried an org key since M1 with nowhere to read a row from; this is that row. `created_at` is the registration date, `plan` the subscribed tier (default `'free'`), `status` `'active'`. One `'default'` row seeded by the migration; no signup path.
- `solutions(id, name, created_at)` — MVP row = today's `demo/sdm` bundle.
- `operations(id, org_id, solution_id FK NOT NULL, name, config jsonb, created_at)` — `config` holds the menu (§5); jsonb column, not a table, until a second consumer demands one.
- Rekey: `configs`/`pages` → `solution_id`; `records`/`rpt_*` → `operation_id`. One migration; seed script updated.
- `page_versions(solution_id, path, version int, def jsonb, readme text, published_by, published_at)` — PK `(solution_id, path, version)`; **append-only, immutable** (activity-history posture).
- `sdm_config_versions(solution_id, version int, config jsonb, readme text, published_by, published_at)` — PK `(solution_id, version)`; same posture (M9). The model's change history, now that the database — not the repo files — is the source of truth for a solution.
- Governance (§2a **resolved 2026-07-20: Option B — bespoke org-tier structure**, RBAC_DESIGN rev 7):
  - `user_roles` keyed `(org, operation, user) → roleIds`.
  - `sol_users` keyed `(user, solution) → level`.
  - Plain auth-tier reads (no SDM, no activities); admin CRUD surfaces built by hand in Console. Governance-solution dogfood remains a possible later migration, not a seam obligation.

## 3. Console app

- **Two-level IA (M7; chrome restandardised M16, org menu + inner panel M17)**: the Console is a *workspace* until a solution is opened.
  - **Workspace level** (no solution open) — the **organisation home**, one nav group headed *Organisation* (M17, Neon's org menu): **Solutions** (our Projects — a plain list with **Open** per row; create is a modal; **no inner panel**, ruled twice on 2026-07-31), **Users**, **Solution users**, **Billing**, **Integrations**, **Settings**. **Operations left this level** (ruled 2026-07-31): an operation runs exactly one solution, so it is administered from inside that solution (below). The operation-scoped admin — menu override, role assignments — stays in the **operation view** it moved into at M11.
    - **Users** — the org pool (`org_users`; server built 2026-08-02, Console surface **built 2026-08-04**: `OrgUsersSection`), rendered straight into the main area. Email · Name · Status · Org admin · Suspend/Remove, with invite and the remove confirm in dialogs. Status carries its meaning in a chip — *invited* is the expected case, not a defect, and *suspended* keeps every grant while locking the person out; reinstating an invited user returns them to *invited*, never to *active*, which would claim a sign-in that never happened. The whole screen is org-admin only and says so to everyone else rather than showing an empty table. This and **Solution users** were briefly one *People* section with an inner panel choosing between them (M17); **that section is retired** (ruled 2026-08-04) — the section holds users, so it is called Users, one nav item, no inner panel. **Solution users left the organisation menu entirely** in the same ruling: who builds a solution is a question about that solution. `SolUsersAdmin` is currently **unmounted** and needs a home inside the open solution before design-plane grants are reachable again. "Members" was drift and is retired too — the binding terms are users / org users / op users. Operation-scoped *role assignments* deliberately stay in the operation view: they belong to an operation, not to the org.
    - **Billing** shows the org's plan/status/registered read-only (the M14 data, on the surface a plan belongs on) over a placeholder for the rest. **Settings** is the M14 profile form. **Integrations** is a placeholder.
    - A placeholder section says so plainly and lists what will live there — the IA is the design; the emptiness is honest, not a stub pretending to be data.
- **Data entry is a dialog, not a form on the page (ruled 2026-08-04)** — creating a solution, an operation, a user, a role, or anything else the Console captures opens a modal over the surface it was launched from. The surface stays what it is (a list of the things that exist) instead of being half list and half empty form, the entry point is one obvious button rather than a form competing with the content for the eye, and cancelling leaves nothing behind. Applies to edits of a single row too; it does not apply to editors whose whole purpose is authoring (SDM sections, the page builder, the menu composer), where the form *is* the content. `SolutionsAdmin` (new solution), `RolesEditor` (create/edit) and `OrgUsersSection` (invite, remove confirm) are the shape to copy.
  - **Solution level** (a solution open) — that solution's design artifacts: **Overview** (landing), **Operations** (M17 — the operations admin scoped to this solution: inner panel lists them, main is the operation view, create fixes the solution link), **Pages** (the builder), **Settings** (M17 — the solution's own profile + danger zone), then the **SDM group** (Record types, Attributes, Workflows, Roles, Menu) and **Workbench** (M15 — the record/activity surface, against the M9 data operation).
    - **The operation view is tabbed (M18)**: the selected operation's header (name, id, linked solution, Open in Runtime app) sits above a strip of **Overview · Users · Menu · Data · Settings**. M11 stacked those surfaces down one scrolling page; an operation's admin no longer fits that way. Built: **Users** and **Menu** (the inherit/override editor). The Users tab is two stacked tables in the order the gates apply — **Op users** (may they enter at all; built 2026-08-04) above **Roles** (what they see inside). They stay two tables deliberately: the gates are independent, and one row-per-user grid would imply otherwise. Its **Add user** control has two affordances for the two tiers — an org admin picks from the pool, an op admin (who cannot read the pool) types an address the server validates — and the **Op admin** checkbox renders for org admins only, because an op admin may never mint an op admin. **Overview** shows identity read-only — *status and owner are not modelled on `operations`*, so they read as unset rather than being invented — and **Data** (archiving, retention, export, purge) and **Settings** (rename, status, owner, delete) are placeholders, to be specified.
  - Opening a solution = `engine.openSolution(id, operationId?)` → `FluxusClient.connectSolution({ solutionId, operationId })` → `enterSolutionScope`. The shell subtree is keyed by `scopeVersion` and remounts so every view re-reads the fresh snapshot.
- **Console shell (M16, ruled 2026-07-30 — industry-console chrome, Neon-style)**: the VS Code frame (activity bar + secondary sidebar + global tab strip) retired — it is a document-editor idiom, and only the page editor is a document editor. Replaced by:
  - **Breadcrumb header**: `Fluxus · <org>` always; in solution scope ` / <solution> ▾` — the crumb is a dropdown listing the org's solutions (switch from anywhere) plus **All solutions** (back to workspace). The **Fluxus wordmark is a button** (M17): from anywhere it returns to the organisation home. The **Data** picker (M9) stays on the header's right in solution scope. The dead workspace search field retired.
  - **One persistent left nav** rendered from a **section registry** — the extensibility seam. A Console section registers `{ id, label, group?, scope: workspace|solution, render, canLeave? }` in `shell/sections.tsx`; the shell renders nav + routes from the registry and never knows a section's internals. Adding a Console surface = one registry entry. Nav contents switch with scope (workspace set vs solution set); the frame never changes. Group headings (e.g. **Shared Data Model**) are flat labels, not collapsible trees — everything one click.
  - **Three columns (M17, amends M16's "inner panels belong to sections")**: nav → **inner side panel** → main, the industry-console shape. The shell owns the *column*; a section fills it by rendering `<InnerPanel>` anywhere in its tree, which **portals** into it. The state stays where it belongs — an SDM editor's list is its *draft*, so unsaved renames and additions show — while the frame stays the shell's, and every section's list sits in the same place: Pages → the page tree (with its Components/Search switcher as the panel head), Record types / Attributes / Workflows → their model lists, Operations → the org's operations. A section with no list renders none and the column collapses — Overview, Settings, Billing, Menu, Workbench, **Roles** (a table in the main area since 2026-08-01, same shape as Solutions: name, id, description, Edit and Delete per row, create/edit in a modal, id generated from the name and read-only afterwards) and **Solutions**, which is a plain list in the main area (ruled 2026-07-31: the org's solutions are the content of that screen, not a sidebar to something else). **Tabs stay a page-editor idiom** inside `PagesSection`, with the bottom console — out of shell state's meaning (`openTabs`/`activeTab` mean open pages only).
  - **Hash routes**: `#/<section>` (workspace), `#/s/<solutionId>/<section>` (solution scope) — location legible, bookmarkable, browser back works. The solution id is **percent-encoded**: ids contain slashes (`demo/sdm`), and unencoded the route re-parsed as solution `demo`, silently opening an empty model (found in the M17 browser smoke, fixed there). One-way sync state→hash via store subscription; hash→state on `hashchange`/boot (a solution route boots via `openSolution` + a name lookup from `solutions.list`). A section's `canLeave` guard (the SDM dirty-draft confirm) runs on any navigation away, nav click or hash.
  - **Solution Overview**: lean landing page (name, id, origin, operations + data-operation note, section links) so entering a solution is arrival, not teleportation into an editor.
  - Dark theme retained — M16 is structure, not re-skin; a visual pass is separable (§10).
  - **Design data (M9, ruled 2026-07-26)**: the model and draft pages are solution-scoped; the **records come from one of the solution's operations**. Console previously connected with an empty record set, so the SDM editor and page preview showed nothing where the Runtime host showed rows — the platform contradicting itself, and authoring hooks/datasources/list columns blind. **Amended M18 (ruled 2026-07-31): the picker lives in the workbench side menu, and nothing is auto-selected.** The workbench's model is the solution's while its records are one operation's, so the control belongs next to the data it governs — the header's **Data** picker is gone, and its label was wrong anyway: it picks an *operation*. The choice stays solution-wide (the page preview reads it, so Console and Runtime still never disagree) and is remembered at `fluxus:page-builder:workbench-operation:<solutionId>`; switching re-opens the solution against that operation and remounts. A remembered operation that no longer exists is dropped rather than carried. **No operation is selected until someone picks one** — the old fallback to the solution's *first* operation bound the Console to a partition nobody chose, and "first" was an unordered read, so it could change between loads. With none selected the record types still list, the grid and record pane say so, and the preview carries a one-line notice. A solution with no operations at all still opens. Activities run normally once an operation is picked: running one is how you test a workflow.
- Host: current page-builder app grows sections; page editing unchanged (drafts = `pages` table).
- **The two Opens follow the two planes** (ruled 2026-07-26). **Solutions → Open** enters the **Console** design scope: author the model and pages, no operation required (authoring is never gated on data — a solution opens with no operation selected, and the workbench's picker binds one when you want records). **Operations → Open** launches the **Runtime app** on that operation, in a new tab: `${VITE_FLUXUS_RUNTIME_URL}/?operation=<id>` (localhost:5173 in dev). One list is "what am I building", the other is "what is running".
- **Operations admin** (workspace level): list/create operations (name + solution) + the Runtime Open above; user→role assignments UI; sol users UI (both over §2 governance tables).
- **SDM editor** (solution level, M7): model authoring — record types (+ custom fields, workflow binding, RBAC read surface), the attribute pool (key/label/type + fk/list/multi/multiline config), workflows + their activities, and role defs. Plain forms over `config.get`/`config.put`; a save persists the whole config, reloads the solution to rebuild the model, and remounts. **Workflows editor** (M8, slice 2, lean): `WorkflowsEditor` under the `sdm/workflows` tab — workflows (id/name/description) with activities nested; per-activity id/name/description/sort_order/record_map/show_condition plus a lean attribute-usage composer (pick pool attribute, toggle required, insert section headings, reorder) and before/after hooks. FluxScript is edited as plain textareas (no DSL tooling yet); per-usage overrides (show_condition/validation/can_waive) and the FunctionDef/seed collections stay hand-edited — deferred.
- **Publish flow**: per-page action → dialog requiring **readme** (release notes, md) → `pages.publish` snapshots the draft def into `page_versions` at `max(version)+1`. Rollback = republish an older version's def as a new version — never delete/edit.
- **Model publish (M9)**: the same surface for the SDM — a toolbar above every SDM section → `config.publish` snapshots the solution's config into `sdm_config_versions`, readme required. One difference from pages: `config.rollback` republishes an older version **and restores it as the draft**, because the config draft is what every host evaluates against (a page draft is the builder's working copy, so it is left alone).
- **Menu editor**: edits the operation's `config.menu` (§5); requires op admin (ruled 2026-08-02; was sol-user `write`).
- **Versions view**: per-page version list w/ readme. Diffing = non-goal.
- Gating (RBAC stage 2): `config.put` / page save / publish / menu edit require sol-user `write`; user/role administration moved to the org and op admin tiers (2026-08-02). Until then: stub-open per env posture.

## 4. Runtime app

- Host: SDM workbench evolves in place.
- Boot: sign-in (built) → operation resolution (a single op-user row auto-selects; picker if >1; MVP: single hardcoded op acceptable) → `connect(operationId)`.
- Renders **published page versions only** (latest per path); drafts never leave Console. Console preview keeps rendering drafts via embedded page-runtime.
- Nav = operation menu (§5), role-filtered.
- **The Runtime app renders published pages only; the workbench leaves it** (ruled 2026-07-27, superseding the 2026-07-20 "stays reachable for now"). The line is *runtime = the authored app, Console = model + data tooling*: raw record access, running any activity, CSV import and the schema navigator are design-plane work, and Console already connects against a data operation (M9), so the workbench lands there next to Pages and SDM and the SDM editor stops authoring blind. Consequences: no menu-addressable "Workbench" item, no record-type list in the Runtime nav, and an operation whose solution has no published pages shows an empty app — the escape hatch is gone by design. **BUILT 2026-07-27 as M15** (§9).
- **The workbench becomes one component** (ruled 2026-07-27) — `<Workbench client user? />` (as built; the `client config` first sketched was redundant — config, adapter and uploads all hang off the client) owning its own context (selected record type, record, activity in flight, CSV/schema-nav state); nothing above it knows those exist. Today's `AppContext` mixes shell state with record state, and that mixing *is* the coupling: the split — session/user + operation + effective menu + current page in a `RuntimeContext`, everything record-shaped inside the workbench — is the extraction. It stayed inside `@fluxus/sdm` at M15 pending a name endorsement; **superseded 2026-08-01** — it is now the `@fluxus/workbench` package (§11.16). Orthogonal to and non-blocking for the deferred `RecordGrid`/`RecordView` page-runtime decomposition (§10) — this is the container step, that is the inner one. **BUILT as M15** — signature
  `<Workbench client user? />`, cluster now at `packages/workbench/src/`, hosted by
  Console's `WorkbenchView`; see §9 M15 and §11.16.
- **Solution branding, not platform branding** (cosmetic MVP; no branding config yet — logo/colours deferred, §10). The header carries an **identity line** (M13): **org name · solution name** on the left — who you work for, which app you are in — the **operation name** as a context chip on the right, then the user menu. ## 5. Menu (amended 2026-07-26: **defined solution-side, overridable operation-side**; original 2026-07-20 ruling was operation-side only)

- The solution's config artifact carries a top-level **`default_menu`** (key name pending endorsement) in the §5 shape below — versioned/published with the model via `sdm_config_versions`, so a prebuilt solution ships working menus. The engine stays menu-blind (`config.put` is `z.unknown()`; `validateConfig` ignores the key); the server validates it with the same §5 rules at `config.put`, roles read from the **incoming** config.
- `operations.config.menu` becomes the **override**: key absent ⇒ inherit the solution default; present ⇒ **whole-menu replacement** (`[]` = explicitly empty). Per-item merge is ruled out — that is where diff semantics and upgrade pain live. Effective menu = `operation.config.menu ?? solution.default_menu ?? []`, resolved at client connect.
- Role-filtering, deny-default, §5 validation, `visibleMenu()` are unchanged and run on whichever menu is effective.

```jsonc
// operations.config
{ "menu": [
  { "label": "Dispatch", "page": "dispatch/board", "roles": ["role_dispatchers"] },
  { "label": "Admin", "roles": ["role_managers"], "items": [
    { "label": "Crews", "page": "admin/crews", "roles": ["role_managers"] } ] }
] }
```

- One level of nesting max (MVP).
- **Item ids (2026-08-01)**: `MenuItem.id` is a stable id, independent of the label — the editor selects and reorders by it, and §5a's per-item overrides need it so a relabel in the solution does not lose an operation's setting. Optional in the type, so menus authored before it still load; the editor fills missing ids in and they persist with the next save. Ids must be unique across the menu (checked in `validateOperationMenu`), and `id` is declared in the tRPC menu schema — Zod strips unknown keys, so an undeclared field would be dropped on save.
- **Editor shape (2026-08-01)**: three columns — item tree, properties of the selected item, preview. The tree is one row per item (label, page or `group`, role count) with drag-and-drop ordering: dropping on the top or bottom of a row places the dragged item before or after it, dropping in the middle of a group row places it inside. A group cannot be dropped into a group (the one-level rule). The preview renders the navigation for a chosen **set of roles** ("View as roles", with All and None) — a user holds several roles per operation and an item shows if they hold at least one of its listed roles, so a single-role preview cannot show what a real user sees. The preview shows navigation only, not page content. Replaces the previous form, which expanded every item with a checkbox per role and had no reordering.
- **Per-item role lists; no `roles` (or empty) ⇒ item hidden** — deny by default (ruled 2026-07-20). Visible iff user holds ≥1 listed role in the operation. Groups: own `roles` gate AND ≥1 visible child.
- Menu roles control **visibility**; page `access.open` (§6) still gates **entry** independently. Two layers, both deny-default.
- Role ids reference the linked solution's `access.roles`; page paths must resolve to **published** versions of the linked solution (ruled 2026-07-20) — both validated at operation-config save.

### 5a. Override direction (agreed 2026-07-31 — **not built**, no schema endorsed yet)

Whole-menu replacement is the MVP and stays as the escape hatch, but it **forks the operation from upgrades**: a release that adds a page adds it to the solution's default menu, and an operation that replaced its menu never sees it — silently, because the operation isn't behind a version, it just lost the channel. The direction is to make the everyday override *subtractive* instead:

- **Groups are the switchable unit.** A solution ships its menu as named groups ("Inspections", "Scheduling", "Admin"); an operation switches a group on or off. Coarse decisions stay cheap, new items land inside a group already enabled, and it lines up with packaging — a solution dependency contributes its group, so "we don't use scheduling" is one switch, not a curated tree.
- **Item toggles are the fine adjustment** inside a group that is on. Inherit everything, turn off what you don't want.
- **Three postures**: *inherit* (default) · *group + item toggles* (everyday) · *whole replace* (escape hatch, labelled as forking off upgrades).
- **Stable item ids: added 2026-08-01** (§5, `MenuItem.id`). This was the prerequisite — without it a subtractive override had nothing durable to name, and relabelling an item in the solution would silently re-enable an operation's "off".
- **What an operation may add**: *structure* — its own groups, labels and ordering, built from items the solution already ships (nothing new is authored, so upgrades still flow) — and, if endorsed, **external links** (a `url` field beside `page`; no design artifact, so no fork).
- **What it may not add: a page.** Pages are solution artifacts; an operation authoring one puts design work in the runtime plane and becomes an unversioned fork — nothing can upgrade it, and "what is running" stops being "release X of solution Y". The pressure is real (some depot always wants one extra screen) and packaging already answers it: that org authors a **thin solution depending on the base one** and the operation runs that. The rule enforces cleanly — an item with neither `page` nor `url` is a group; an item with a `page` must resolve to a published page of the solution the operation runs, which the server already validates.
- **Naming follows the shape**: one tree per solution ⇒ *Menu*; if groups become the switchable unit and a solution can ship several, the Console section becomes *Menus*. Decided when the shape is built, not before.
- **Expressions on items: deliberately not now.** Roles already do the visibility work, and per-item conditions make "why can't this user see this" much harder to answer. The storage shape does not preclude adding one later.

## 6. Page access control (RBAC stage-2 surface, per RBAC_COMPACT)

- `PageDef.access.open: [roleIds]`; default deny once the solution declares `access.roles`; no roles section ⇒ open (adoption posture).
- Enforcement: server filters the Runtime `pages.list` snapshot to openable published versions per `context.user.roles` (upgrades the "client interim" — cheap once roles are in context). Client menu filtering is cosmetic on top.
- Console preview exempt (design plane; `read` sees all).

## 7. Auth/RBAC wiring (existing seams)

## 10. Non-goals (MVP)

- Solution publish/upgrade + version pinning per operation (operation always runs latest published pages; seam = future `pinned_version` on operations); catalogue/import; org management UI; page-version diffing; row/field-level permissions (RBAC_COMPACT exclusions); multi-org.
- M10 deferrals: header operation **switcher** (boot stays `?operation=` / default); branding beyond names (logo, colours); per-item menu merge (ruled out, not deferred); workbench decomposition into page-runtime components; component-library adoption (needs a dependency ruling).
