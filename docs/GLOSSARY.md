# Fluxus — Glossary

Canonical definitions. If a doc or discussion uses one of these terms differently, this file wins; if a new term earns repeated use, add it here.

## Model

- **SDM (Shared Data Model)** — the single definition of record types, attributes, workflows, and activities; the platform's unit of scope (records, scripts, and the DSL all bind to one SDM). The canonical source of truth; everything else is a projection over it.
- **Record type** — a collection definition (e.g. `rt_assets`): custom fields, FK refs, and a reference to its workflow. Named plural — it names a collection.
- **Record** — one instance of a record type: `id`, `typeRef`, custom field values, and its activity history.
- **Custom field** — a typed field on a record type (`text`, `int`, `bool`, `date`, `fk_ref`, …) with optional constraints (`required`, `unique`, `immutable`, `indexed`).
- **Attribute** — a standalone, reusable definition of a capturable input (label, type, type_config). Activities reference attributes; attributes are shared across activities.
- **Composite attribute** — `type: "composite"`: one question's row of answer slots (a paper form's Item + OK / Reference / Comments) as a single attribute. `type_config.attributes` is a list of usage wrappers over **real pool attributes** (same shape as an activity's list; `required` / `can_waive` / `validation` / `show_condition` per cell; any type except `composite` and `reference`). The question stays an ordinary attribute usage in its activity, keeping show_conditions between questions. A cell is addressed `attr.sub` — `'.'` is reserved in keys as the path separator. Cells live nested on the history entry, flatten to one reporting row per cell (dotted key), and render stacked (question, inputs beneath). Born from the MR014 checklist trial (2026-07-18; grid-level first cut reworked same day).
- **Section marker** — presentation-only entry `{ "section": "…", "description": "…" }` in an activity's attribute list: renders as a heading over the usages that follow, captures nothing, ignored by headless callers. The grouping half of what the grid composite once conflated with data shape.
- **Attribute type registry** — the engine-code declaration (one entry per attribute type) of each type's descriptor sub-fields, accepted `type_config` keys, and whether `multi` is legal. The machine-readable companion the SDM baseline asked for once `type_config` shapes stopped self-documenting as table columns; read by the client uploader, `validateSubmission`, and `validateConfig`.
- **File descriptor** — the by-value bag a `file`/`photo` attribute stores in place of the bytes: `storage_key`, `name`, `mime`, `size`, `hash` (SHA-256), plus for photos `width`/`height`/`thumb_key` and optional EXIF `lat`/`lng`/`taken_at`. Composite-shaped and dot-addressed (`before_photo.taken_at`), stored by-value so history entries stay self-contained; the bytes live in the blob store, never in the pipeline.
- **Multi (cardinality)** — `type_config.multi: true`: the attribute's captured value is always an array, and `required` means ≥ 1 item. One flag for every type except `composite`; the single spelling of cardinality platform-wide (replacing the deleted list-only `selection` key).
- **Workflow** — the ordered set of activities available for a record type. One workflow per record type.
- **Activity** — the unit of action and the only way data changes. Has attributes (its inputs), an optional `record_map` (CREATE/UPDATE/DELETE/GET; null = log-only), and before/after hooks. In headless mode, an activity is a callable function whose attribute list is its parameter signature.
- **GET activity** — `record_map: "GET"`: a query activity; attributes are parameters, a `returns` expression produces the response. Never mutates (validator-enforced); logged like every activity (async, retention-managed). The platform's read path — apps call GET activities instead of ad-hoc APIs.
- **Activity history** — the append-only per-record log of executed activities and exactly what the user entered. The audit spine — and the platform's *only* log: there is no separate logging subsystem (see Class, Execution entry).
- **Class (`direct` / `system`)** — the nature of a record type and, derived from it plus authorship, of every history entry. Direct = business truth, never trimmed; system = the platform's own doings (apps, notifications, engine-authored entries), retention-managed by governed policy. Never edited, either class. (Design direction, July 2026 — lands with the backend.)
- **Execution entry** — the engine-authored, system-class history entry appended alongside a submission when an after hook did something observable; its attributes state plainly what the machinery did ("record XYZ created", "email sent", warnings). Replaces the "log stream" and "outbox table" concepts.
- **Watch** — the single escalation valve for capture: a per-activity dial that records more (validation failures, read service calls, payloads) when investigating. No other logging switches exist.
- **Hook** — DSL script on an activity. **Before hook** = gate: validation only, `fail("msg")` vetoes, `warn("msg")` soft-stops (user confirms or cancels), nothing persists. **After hook** = effects: record mutations (transactional) and service calls.
- **Anchor record** — the record an activity is run against; what `context.record` points to inside its hooks. CREATE activities have no anchor until the record exists (the after hook sees the created record).
- **Waiver (`can_waive`)** — a per-usage escape hatch on a required attribute: the user declares the value unavailable ("can't provide") with a mandatory reason instead of entering fake data. The record field is never written. On the entry, a waived attribute is one attribute, one row: value `null`, reason alongside it as `waive_desc` (ruled 2026-07-12; the browser POC's separate `waived` map remains until the backend). Known-missing beats plausible-wrong.
- **Compensating activity** — the only way to undo. History is never edited, so a post-commit mistake is reversed by a modeled activity (`act_cancel_…`) that posts the correction, accounting-reversal style. There is no generic platform undo (after-hook effects and queued service calls are not invertible), and no admin surface may edit or remove history.
- **Workbench (`@fluxus/workbench`)** — the out-of-the-box vanilla UI every SDM gets for free (record type list → records grid → record view with activities). The generic runtime face of whatever model the config carries: a usable tool with zero app-building, and the proving ground for DSL features. Pages are the optional bespoke layer on top — apps come and go, the workbench comes with the model. (Decided July 2026: name kept, positioning explicit.) Shipped as one mountable component; **the Console hosts it** (M15, 2026-07-27 — raw record access and arbitrary activity runs are design-plane work), and it became its own package at the 2026-08-01 restructure.
- **Activity engine (`@fluxus/engine`)** — the shared, host-agnostic package owning the activity pipeline (`runActivity`: availability gate → before hook → record_map mapping → history append → after hook), the `Store` contract, the DSL bridge, and config validation. Extracted from the then-`@fluxus/sdm` package (now `@fluxus/runtime`) at the Extraction milestone (July 2026). There is exactly one pipeline; hosts import it, never reimplement it.
- **Host (of the engine)** — an application that constructs an Engine (`createEngine({ store, config, services })`) and drives activities through it: the workbench, the Console, the Runtime app, the server (`@fluxus/server`, headless callers). Hosts own everything the engine deliberately doesn't: UI state, notification surfaces, warning channels, service module implementations. Since backend stage 2, browser hosts are **client hosts**: their Store is a partition snapshot fetched through `@fluxus/client`, their engine evaluates expressions only, and every mutation round-trips the server's `activities.run`.
- **App-triggered run** — an activity run started by an app's named callback rather than a workbench form. The callback contract is **(record, one data object)**; a UI activity opens the standard capture form, a non-UI activity (no attributes) passes straight to the hooks. (Extraction stage 2, ruled July 2026.)
- **System log (`system_log`)** — reserved attribute on a history entry holding the lines hooks noted via `services.logger` during the run. The pipeline is the log; there is no separate log store. Lines are discarded if no entry commits.

## Language

- **DSL** — the one Fluxus scripting language (working name *FluxScript*): JS/SQL blend, no lambdas, case-insensitive, null-safe, no visible async. Three tiers: expressions → queries → scripts.
- **Four roots** — the entire environment a script can touch, dependency-injected by the host: `context` (user, record, activity, workflow), `attributes` (captured values), `records` (SDM data graph), `services` (add-on modules).
- **Datasource** — any DSL expression evaluating to a list; powers `List` attributes and page bindings. May be an inline literal, a `records` query, or a service call.
- **Show condition** — DSL expression deciding applicability. On an attribute usage: whether the attribute is presented (UI) or accepted (headless); errors leave it visible. On an activity: whether the activity is offered/invocable at all — the **availability gate**, re-checked as the first step of the activity pipeline; `attributes` is unavailable (runs before capture) and errors fail closed.
- **`queue`** — keyword marking a service call as fire-and-forget; dispatched only if the surrounding transaction commits (outbox pattern).
- **Service module** — the unit behind the `services` root: manifest (name, description, functions with params + `kind`) plus implementation. `kind: read` = pure query, callable anywhere; `kind: effect` = changes the world, after hooks only, prefer `queue`. Manifests make service calls schema-validatable (existence, arity, purity) at config-save time.
- **`callbackData`** — embedding-point extra root (like `value` in validation rules). In hooks: the one data object of an app-triggered run, `null` on direct runs. In page callback scripts: the packed component payload `{value, data}`. Untyped — its shape is the solution builder's contract with their component.
- **Scope-blind** — scripts never name their org, repo, or SDM; scope is injected. Locked invariant.
- **Schema-aware validation** — every script checked against the SDM at config-save time (unknown types/fields/shapes fail before runtime).

## Pages and apps

- **Page** — a layout of panels with slots, each slot wired to a component; defined declaratively, rendered by the run-a-page cluster (`@fluxus/page-runtime`).
- **Component manifest** — a component's contract: name, version, prop schema (static-config, dynamic-data with item shapes, callbacks).
- **ComponentContainer** — the runtime adapter between a slot's wiring config and the SDM-blind component; resolves dynamic props, wires callbacks.
- **Wiring (slot config)** — the per-page adapter binding a component's ports to a specific SDM, in FluxScript everywhere (2026-07-12): one expression per dynamic prop (datasource posture — reads only), one script per callback. The stored artifact is the source text; picker UIs merely write it.
- **Callback (page)** — a component's named output port, bound to a FluxScript script receiving the payload as `callbackData` (`.value` / `.data`). "Callbacks", not "actions" (naming ruling): scripts effect UI via `services.page` and mutate only by requesting an activity run.
- **`services.page`** — the page-host-only service module: `setContext`, `hideComponent`. A page callback, a hook, and a future non-UI workflow differ only in which service modules their host provides.
- **`services.activities`** — the host-neutral activity surface: `run(activityId, record, data)`. Same manifest in every host, host-specific implementation (page host opens the capture form for UI activities; a headless host takes attributes directly). Scripts that only run activities are host-portable.
- **validatePage** — save-time validation of a page file against the model: component names vs the registry, bindings vs component schemas, expressions/scripts vs the SDM schema + declared roots, literal activity ids vs real activities. The page counterpart of `validateConfig`.
- **App (module)** — a coarse-grained reusable component (e.g. calendar scheduler) shipped with a manifest; rewired per SDM through slot config, never rewritten.
- **Activity spine** — the property that data + behaviour + audit share one backbone because every surface mutates only via activities.
- **Page runtime** — the run-a-page half of the page machinery (named 2026-07-19): PageRenderer + ComponentContainer + the component registry + the page expression host + the activity capture form — everything a host embeds to turn a stored page definition into working UI against live records. Distinct from page *editing* (editor, palette, Monaco), which stays Console-side. Extracted as `@fluxus/page-runtime`; the Console app embeds it for preview, the Runtime app as its main surface.

## Organisation (future)

Naming locked 2026-07-19: **org / solution / operation**. Design plane and runtime plane are distinct — a solution is authored once; operations run it.

- **Org** — the tenant: users, auth, billing, org-scoped reporting. Owns repos (design plane) and operations (runtime plane). Since M13/M14 (2026-07-27) an `orgs` row backs the id that `operations.org_id` / `user_roles.org_id` have carried since M1: `name`, `contact_email`, `plan` (the subscribed tier — billing itself is later), `status`, and `created_at` as the registration date. Console's **Organisation** settings surface reads and edits it, and both apps show the org name. **Registered by the platform plane since 2026-08-03** — `platform.registerOrg` writes the org and its owner in one act, which is what makes a second org possible; there is still **no signup**, and the org id is a permanent URL slug because the apps read their org from `/o/<orgId>/…`.
- **Org owner** — the org's first `org_users` admin, set when the org is registered, and recorded as `orgs.contact_email` so the row itself answers whose it is. Deliberately **not a separate level** (2026-08-03): the authority is org admin's, and a distinct `owner` value would need transfer and demotion rules nothing needs yet. They invite everyone else.
- **Platform plane** — the vendor's tier, above every org (named and built 2026-08-03). Answers the two questions the org tier structurally cannot: who creates an org, and who sees across orgs. Its app is **`@fluxus/platform`**; eventually also where usage, billing and cross-org solution entitlement live.
- **Platform admin** — who may use the platform plane: us. Slots into the ladder as op admin → org admin → **platform admin**. Backed by an **env allowlist** (`FLUXUS_PLATFORM_ADMINS`), not a table — a table would recreate one tier up the chicken-and-egg `npm run bootstrap` exists to escape. The one gate that does **not** fall open when auth is unconfigured, because it guards every org from everyone rather than one org from its own people.
- **Solution** — the design-time artifact: one coherent, shareable bundle of SDM + workflows + pages + role *definitions* + the **default menu** (`default_menu` in the config artifact, M10 2026-07-26 — operations inherit it unless they set a whole-menu override; **direction 2026-07-31**, CONSOLE_RUNTIME_SPEC §5a: the default menu becomes named **menu groups** an operation switches on or off, with per-item toggles inside an enabled group — replacement stays only as an escape hatch, because it forks the operation off the upgrade channel. Operations may add structure and external links, never a page: a new page is always a solution). Contains **no data, no users, no role assignments**. The unit of sharing/import and sol-user grades; what gets published into an operation. Carries **provenance** (M12, 2026-07-26): `origin` = `authored` (this org) | `installed` (the Catalogue), plus `origin_ref` — the opaque catalogue lineage of installed work. Its parts are versioned individually — pages via `page_versions` (M3), the model via `sdm_config_versions` (M9, 2026-07-26): append-only, release notes required, rollback republishes. A **solution-level** publish that bundles them into one release is still not designed. The database holds the authored truth; git carries code and migrations. Example: "Electrical Inspections" — what an inspection *is*, how it flows, what screens exist, what a Dispatcher may do.
- **Operation** — the runtime unit: a business unit running one solution, owning its own record partition, users, role *assignments*, and files. Two plumbing operations can run the same plumbing solution with disjoint data and people. **Endorsed replacement for the unendorsed "scope"** — the partition key becomes the operation id (code rename pending).
- **Hierarchy** — design plane: org → solutions. Runtime plane: org → operations, each running a solution. **No repo tier** (dropped 2026-07-19 — solutions carry their own sharing and permissions; folders as pure navigation may return if an org's solution list needs organising). Domain structure (divisions, projects, contracts) is the org's own solution/operation naming plus record types inside SDMs. Not yet built; the scope-blind invariant exists so its arrival changes no scripts.
- **Console app** — the design-plane app (named 2026-07-19). It authors solution-scoped artifacts but binds to **one of the solution's operations** for the records it builds against (2026-07-26) — a model or page authored without data is guesswork, and Console disagreeing with the Runtime host about what exists is a defect. Where solution builders author solutions (SDM, pages, workflows, roles) and administer the platform (sol-user grades, user→role assignments, operations, publishing solutions into operations). Built as **`@fluxus/console`** (named `@fluxus/page-builder` until the 2026-08-01 restructure, when the name stopped describing the package: the page builder is one editor inside the Console).
- **Runtime app** — the runtime-plane app (named 2026-07-19): what end users sign into. One app that renders whatever solution the caller's operation runs — menu, pages, activities. Built as **`@fluxus/runtime`** (named `@fluxus/sdm` until the 2026-08-01 restructure — it holds no model, so the old name misled). Since M15 it renders published pages only; end users see the solution's branding, not the platform's.
- **Platform app** — the platform plane's app (2026-08-03): registers orgs and their owners, lists every org. A separate app rather than a Console section by design — the Console is scoped to one org by construction, so folding cross-org data into it would ship tenant-spanning code in every customer-facing deploy. Built as **`@fluxus/platform`**; first cut is org list + register.
- **Catalogue** — reserved (not built): the browsable collection of solutions an org or marketplace offers for install. The collection is the catalogue; the item is a solution.

## Packaging and upgrades (direction, agreed 2026-07-27 — none built)

Settled in the blueprint session (see [BLUEPRINT.md](BLUEPRINT.md)); recorded here so the terms stay stable.

- **Release** — one numbered snapshot of a whole solution: the model plus a chosen set of page versions, cut deliberately by the solution owner. The unit operations run; the per-page/per-config version histories are the author's working record underneath.
- **Pinning** — an operation staying on a chosen release (or component version) until it opts to upgrade. No forced upgrades — owner autonomy. An unpinned operation follows latest, which is today's behaviour as the default case. Known open problem: a release that changes the model needs a data-migration story before a live operation can move.
- **Solution connector** — a hook in one solution that calls an activity in another. The target activity's attribute list is the contract, the committed source activity is the trigger, a field mapping is the wiring; rides the existing after-hook `queue` machinery. Vendors may pre-ship connectors between their own solutions. Invariant: **solutions exchange data only by calling each other's activities, never by reading each other's records.**
- **External connector** — the connector picture with one end outside the platform. Inbound: an external system calls a Fluxus activity (the existing headless door; needs machine credentials — API keys with roles — not built). Outbound: a hook calls an external API via an HTTP service module (the registry is the designed slot; module not written). A thin **gateway solution** may front an org: its activities are the stable public contract, internal connectors fan out to the operational solutions. The Fluxus-side contract is always an activity — every integration lands on the audit spine.
- **Entitlement** — reserved: the record of who may run what — copy protection by licence check, not DRM; the basis for billing and revenue share. Waits for a second party to exist.
