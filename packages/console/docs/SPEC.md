# @fluxus/console — Living Spec

Current design truth for the **Console app** — the design plane: authoring solutions and administering the platform. Updated in the same commit as any behaviour/design change (see root CLAUDE.md). The layout editor has its own full spec: [LAYOUT_EDITOR_SPEC.md](LAYOUT_EDITOR_SPEC.md). The wiring design rationale and rulings live in [PAGE_WIRING_DESIGN.md](PAGE_WIRING_DESIGN.md); the mechanisms it specifies (expression host, callbacks, `services.page`/`services.activities`, `validatePage`, the renderer) live in **`@fluxus/page-runtime`** since the 2026-07-19 extraction — see that package's [SPEC](../../page-runtime/docs/SPEC.md). The record surface it hosts is **`@fluxus/workbench`** — see [its SPEC](../../workbench/docs/SPEC.md).

Renamed from `@fluxus/page-builder` at the 2026-08-01 restructure: the package is the whole Console, not one of its views. The page builder survives as the **page editor inside it** (`src/platform-components/page-builder/`) — that directory name still means the feature, not the package.

## Shape

Two layers under `src/`:

- **`platform-components/shell/`** — the Console shell (industry-console chrome, M16; three columns since M17): `HeaderBar` (breadcrumb + solution switcher; the operation picker left it at M18; the signed-in identity sits hard right), `SideNav`, `InnerPanel` (the section's list column), `ContentArea`, and the router. **Two-level IA (CONSOLE_RUNTIME_SPEC §3):** the store's `solutionId` splits the shell into *organisation* mode (Solutions/Users/Billing/Integrations/Settings) and *solution* mode (Overview/Operations/Pages/Settings, then the SDM group and Workbench — `SolutionOperationsSection` mounts the scoped `OperationsAdmin`; `SolutionSettingsSection` edits its name over `solutions.update` and holds the delete danger zone, whose server side is a TODO). Both sets come from the **section registry** (`sections.tsx`) — `{ id, label, group?, render, canLeave? }`; the nav, the content area and the hash router all render from it, so adding a Console surface is one entry. `enterSolutionScope`/`exitSolutionScope` toggle the scope; `scopeVersion` keys `shell-body` so opening/switching a solution (or an SDM config save) remounts every solution-scoped view to re-read the fresh snapshot. Hash routes: `#/<section>`, `#/s/<solutionId>/<section>` — the id segment is **percent-encoded**, because solution ids contain slashes (`demo/sdm`) and an unencoded one re-parses as a different solution.
  - **The inner panel** (`InnerPanel.tsx`, M17): the shell owns the *column*, sections fill it. A section renders `<InnerPanel title actions? head? flush?>` anywhere in its tree and it **portals** into the column — the items are the section's own state (an SDM editor lists its *draft*, unsaved renames included), so lifting them into the shell would be a lie about where they live. The portal host is a module-level div created once and moved into whichever slot is mounted, so the target is live from the first render and survives the `scopeVersion` remount. A section with no list renders no `<InnerPanel>` and the column collapses (`:empty` on the host) — Overview, Settings and the Menu editor are plain two-column pages.
  - The tab strip (`TabBar`) and bottom `ConsolePanel` are **page-editor** furniture, owned by `PagesSection`; the store's `openTabs`/`activeTab` mean open pages, nothing else. The panel takes a `summary` and `children` and renders what it is given (falling back to the idle `>` prompt when empty) — it stayed a decorative shell from the prototype until 2026-08-11, when `PagesSection` began filling it with page findings; the shell itself still knows nothing about pages.
- **`platform-components/page-builder/`** — the editor: PageExplorer, PageEditor, ComponentsPanel, the layout editor, `ExpressionDialog.tsx`, `persistence.ts` (the save path), `PageProblems.tsx` (every page's findings, in the bottom panel). Mounts as a **solution-level** activity. Rendering and validation are imported from `@fluxus/page-runtime` (`PageRenderer`, `componentManifests`, the validators via the `pageRuntime` handle).
- **`platform-components/admin/`** — the organisation-level surfaces over `ConsoleClient`, routed by `AdminView`: **Solutions**, **Operations**, **Users** (`OrgUsersScreen`, from `platform-components/users/` — see below), **Billing** (`BillingAdmin` — the org's read-only plan + placeholder), **Integrations** (placeholder) and **Settings** (`OrganisationAdmin` — the profile form). `Placeholder.tsx` is the shared "not built yet, here is what will live here" card. `SolutionsAdmin` is a **plain list in the main area** — no inner panel (ruled 2026-07-31, twice): name, id, origin, operation count and **Open**, with **New solution** in the header opening a modal (name + id; the id is permanent, so it is only settable there). `OperationsAdmin` takes a `solutionId` and is **no longer an organisation section** (ruled 2026-07-31): it is mounted by `SolutionOperationsSection` inside the open solution, filtered to that solution, with the solution picker dropped from create and the operation view in the main area. **The operation view is `OperationView` (M18)** — a header (name, id, linked solution, **Open in Runtime app**) over a **tab strip**: **Overview** (identity read-only; status and owner are *not stored yet* and say so), **Users** (`OperationUsersScreen` — op users with their roles inline, plus op admins read-only), **Menu** (`OperationMenuSection`), **Data** (placeholder — archiving, retention, export/import, purge) and **Settings** (placeholder — rename, status, owner, delete). It is keyed on the operation id, so switching operations resets the tab and every tab's fetch. M11's stacked page (Overview + menu + assignments down one scroller) is what the strip replaces; the standalone `MenuAdmin`/`AssignmentsAdmin` panels and the `admin/menu`/`admin/assignments` tabs were deleted at M11 and stay deleted. Only Users and Menu are built — the other three are `PlaceholderCard`s to be specified. `OperationMenuSection` carries the M10 **inherit/override posture** (§5 amended): inheriting shows the solution's `default_menu` read-only (`MenuPreview`) with **Override for this operation** (copies it into the editor); overriding shows the composer with **Save override** / **Revert to solution default** (drops the `menu` key — absent means inherit, `[]` means explicitly empty). The item composer itself is the shared `MenuItemsEditor` — since 2026-08-01 three columns: item tree with drag-and-drop ordering, properties of the selected item, and a preview of the navigation for a chosen set of roles ("View as roles"). Items carry a stable `MenuItem.id`; the editor fills in ids for older menus and they persist on the next save (CONSOLE_RUNTIME_SPEC §5).
- **`platform-components/users/`** — the whole user surface (built 2026-08-04, replacing the four first-cut components). **One pattern at three tiers**: each screen shows the tier above **read-only**, the list it governs **editable**, and **Invite**, which only ever adds a person to the organisation and carries no admin connotation anywhere it appears. Screens compose and hold no table markup of their own:
  - `OrgUsersScreen` — *All users* · *Org admins* · *Sol admins*. Mounted by `AdminView` under the organisation's **Users** section.
  - `SolutionUsersScreen` — *Sol admins* (read-only; appointed at the organisation, because that is an exercise of org authority) · *Op admins* for this solution's operations. A section-registry entry inside the open solution.
  - `OperationUsersScreen` — *Op users* with roles inline · *Op admins* (read-only). The operation view's **Users** tab.

  Under them: `tables/` renders one list each and is **reused across screens** — a `readOnly` flag is the only difference between the two places a list appears, so the same component cannot disagree with itself about what a list means; `dialogs/` holds every data entry (a popup over the screen, never an inline form — ruled 2026-08-04) plus the shared `Dialog` shell; `shared/` holds the tab strip, the `ListHead`/`EmptyList`/`StatusPill` primitives and `useUserScreen`, the load/act cycle every screen repeats (**nothing optimistic** — the server owns these rules and an appointment can bounce off a tier check).

  Rules the screens encode: **an empty list always says what the emptiness means** ("nobody may enter this operation"), never "unconfigured"; a **read-only tab always says where its list is edited**, or it reads as broken; **who may act is rendered from `me()`** (`orgOwner`/`orgAdmin`/`opAdmin`) and re-checked server-side on every call; and a caller who cannot read the organisation's people gets a **typed address** where one who can gets a picker — the server answers for the pool and its refusal is the feature.

  **The pool is `User[] | null` everywhere, and `null` means "you cannot read it"** (2026-08-09). Every appointing table takes the pool with that type and passes it straight to `AppointDialog`, whose two modes hang off exactly that distinction: an array is a picker, `null` is a typed address. The tables previously collapsed `null` to `[]` before handing it over, which turned "cannot browse" into "nobody is there" — a picker with no options and a disabled button, indistinguishable from an empty organisation.

  **The fresh owner is the path this fixed** (2026-08-09, and the reason the distinction matters). A newly registered org has an owner who holds no grants — USERS.md §7 says that is normal and that this screen is where they appoint the first org admin, including themselves. But the owner is deliberately not an org admin, so they cannot read the pool, and the empty picker meant the one appointment the screen exists for could not be made. `OrgUsersScreen` now: reads the **org-admin roster** for the owner (the server answers them since the same date), passes `users={null}` so appointment is by typed address, shows them **Invite** (whoever may appoint may invite — `users.invite` has always admitted the owner), and prints their own address in the note beneath, since appointing themselves is the usual first act.

- **`platform-components/sdm-builder/`** — solution-level SDM editor (slice 1): `SdmView` routes the registry ids `record-types|attributes|workflows|roles|menu` to `RecordTypesEditor`/`AttributesEditor`/`WorkflowsEditor`/`RolesEditor`/`MenuEditor` under one model-publish toolbar. Each editor's master list is an `<InnerPanel>` (M17) — record types, attributes and workflows list in the shell's second column, detail in the main area; **Roles is a table in the main area** instead (2026-08-01, like Solutions): no inner panel, one row per role (name, id, description) with **Edit** and **Delete**, and create/edit in a modal. A role's id is generated from its name at creation (`role_<plural>`) and is read-only afterwards, because assignments, menu items and page access lists are stored against it. `RoleDef.description` is documentation only (a workflow's activities stay nested in the detail; Menu has no list) (M10 — edits the config artifact's `default_menu` over `MenuItemsEditor`; empty menu drops the key; validated server-side like the rest of the config). Each edits a local clone of `sdmClient.config` and **saves per entity** (2026-08-08): `useSolutionConfig` exposes one saver per collection (`saveAttributes` / `saveRecordTypes` / `saveWorkflows` / `saveRoles`, and `saveDefaultMenu` for the config's one non-collection field), which diffs the draft against `useLoadedConfig()` — the config as it stood at mount — and issues `putAttribute`/`deleteAttribute` and friends for what actually changed, then `refreshSolutionViews()` (→ `reloadSolution` → remount). Whole-config `saveConfig` (`config.put`) survives on the client as the **import** path only; no editor calls it. This is what ends the lost update: two people editing two different record types both keep their work, where the whole-config save silently dropped whichever landed first. Consequences worth knowing: puts run before deletes, and a **rename is put-new + delete-old**, so renaming something still referenced fails on the delete (the same dangling reference the whole-config save failed on, one step earlier); a save that fails part-way leaves the entities already written saved, and Save can simply be pressed again. A record type's workflow binding is mandatory (the engine resolves `workflow_ref` at save) — the editor offers no "(none)", only a disabled placeholder until one is picked. **Creating a record type is a dialog** (2026-08-05, per the data-entry-in-dialogs rule): the panel's **New** opens a popup collecting name, id (generated `rt_<plural>` from the name until typed over, duplicate-checked), description and workflow, and only then appends it to the draft — a half-typed type never sits in the list failing the save. The record-types panel also carries a **filter** (`.panel-filter`, shared panel chrome in `InnerPanel`) matching name, id and description; it filters the rendered subset only — selection stays an index into the draft, so hiding rows never renumbers it. Workflow/activity/hook (FluxScript) authoring is deferred. `AttributesEditor`'s **list** branch edits `type_config.datasource` (2026-08-10) — a FluxScript expression yielding the choices, which is what the capture form renders and what `validateSubmission` re-runs server-side to check the submitted value ([DATA_THROUGH_ACTIVITIES §3](../../../docs/DATA_THROUGH_ACTIVITIES.md) tier 1). It wrote `type_config.values` before that, a key nothing in the platform reads, so every Console-authored list attribute rendered an empty picker and failed closed at submit (`'<key>' has no datasource`). An existing `values` is shown read-only rather than dropped; nothing writes one afresh. `WorkflowsEditor`'s record-map select offers **GET** (2026-08-10), which replaces the after-hook field with the **`returns`** expression and clears the other on a switch, so the draft never carries a combination `validateConfig` rejects — a GET must have `returns` and cannot have an after hook. **Editing guardrails:** a module-level dirty registry in `useSolutionConfig` (`sdmDirty` + the `useDirty` hook every editor's dirty state mirrors into) backs the registry's `canLeave` guard, which confirms before any navigation away throws an unsaved draft out. Dirty is **per editor, not per selected item**: an editor's draft is a clone of the whole config taken at mount, and selecting a different record type/workflow/attribute is a local index change — so an edit to one item keeps Save enabled while you inspect another, and Save writes every pending edit across all of them — one call per changed entity, not one call for the model. Guardrails, continued:  `fk_ref` custom fields pick their target record type and display field from the draft (selects, not free text — display field disabled until a target resolves); empty/duplicate ids (record types, workflows, the selected workflow's activities, roles, **and attribute keys** — added 2026-08-08, since a per-entity save addresses each attribute by its key) disable Save and show one `admin-error` line (`idProblems`); and the three destructive actions (record type, workflow, activity) arm on first click ("Really delete?") and fire on the second, disarming on any selection change. **Delete vs Remove** (2026-08-01): *Delete* destroys the object (role, record type, attribute, workflow, activity, page, solution, operation); *Remove* detaches something that still exists elsewhere (a menu item, a user's role in an operation). Labels follow that split.

- **`platform-components/workbench/`** — the workbench, hosted (M15, CONSOLE_RUNTIME_SPEC §4). `WorkbenchView` is a thin host: it mounts `<Workbench>` from `@fluxus/workbench` under the `workbench` section, passing `sdmClient`, `currentSession`, and — since M18 — the **operation choice** (`operationId`, `operations`, `onSelectOperation`). Raw record access, running any activity, CSV import and the schema navigator are design-plane work, so they belong on this plane — and the SDM editor two clicks away stops authoring blind. The picker itself is the workbench's own side menu (ruled 2026-07-31): selecting re-opens the solution against that partition and bumps `scopeVersion`; selecting none reconnects with no partition. The host no longer carries a "No data operation" screen — the workbench says it, in the panes it applies to. Everything record-shaped lives inside the component's own context — this package owns none of it. The workbench brings its own light chrome into the Console's dark shell; a themed workbench waits on the branding config.

The app component library (AppHeader, InventorList, InventorProfile, Map, WorkOrderList and their prop schemas) moved to `@fluxus/page-runtime`; `src/components/index.ts` re-exports it for the `MyComponents` mount API (`src/api.ts` — the original react-in-html mechanism for embedding registered components, and the real entry: index.html loads it and mounts `Shell`; `src/main.tsx` is a dead POC leftover). The palette registries (`sessionComponents.ts`, `componentSchemas.ts`) stay here as separate lists by standing decision (deriving the three registries from the manifest is a floated cleanup, not agreed).

## SDM runtime (Extraction stage 2; repointed at backend stage 2; slimmed at the page-runtime extraction)

`src/sdm-runtime/engine.ts` holds the platform singletons (fork 2: never in React state). `initSdmRuntime()` (kicked off by `api.ts` at module load; every `mount` awaits it) now only runs the auth gate and creates the solution-independent `consoleClient` — the Console **boots into workspace mode** with no solution connected. Opening a solution calls `openSolution(id)`, which assigns the design-scoped singletons; `reloadSolution()` re-runs it after a config save:

- **`consoleClient`** — `ConsoleClient` for the workspace admin surface (solutions/operations CRUD, publish/versions/governance). Created once at boot; solution-independent.
- **`sdmClient`** — `FluxusClient.connectSolution({ solutionId, operationId })` (design plane: config + draft pages by `solutionId`, **records from the chosen operation** — M9) into the engine's `MemoryAdapter`. Reassigned on each `openSolution`; undefined in workspace mode (only solution-level views read it). `saveConfig` persists the SDM config; `publishConfig`/`configVersions`/`rollbackConfig` back the SDM toolbar's Publish/Versions dialogs.
- **Organisation settings** (M14, CONSOLE_RUNTIME_SPEC §1a): `OrganisationAdmin` under the **Settings** section — a Profile form (**name only**, over `ConsoleClient.putOrgProfile`) plus the org id and the **owner**, read-only. *Contact email* went with its column (migration 0018): it was born identical to the owner's address and read by nothing. The owner is not editable here because changing it is ownership transfer, and this screen is org-admin work — an editable field would let an org admin promote themselves to the root that appoints org admins. The read-only **plan/status/registered** reads under **Billing** since M17 (same `orgs.get` data, the surface a plan belongs on). Plan and status are ours to set, never the org's, so they are display-only; there is no create — signup needs user → org resolution the auth tier does not do. `HeaderBar` shows the org name beside the Fluxus wordmark at **both** IA levels, and the wordmark itself is the way back to the organisation.
- **Signed-in identity in the header** (2026-08-02): `HeaderBar`'s right end names who you are acting as — avatar initial plus display name (falling back to email), the full `name · email` on hover. It reads `currentSession` from the engine, assigned by `initSdmRuntime()` before the first mount and constant for the life of the page, so no subscription is needed. **The three postures are distinct and must stay that way:** auth unconfigured shows *"Demo — no auth"* (the API is open and roles are not enforced — not the same as being signed out), auth configured with no session shows *"Not signed in"*, and a live session shows the user. The Console previously showed nothing at all, while the Runtime had an identity line since M13; since both apps share one Neon Auth origin and cookies ignore port, a session established in either is presented by the other, and the only way to discover your Console identity was to open the Runtime. There is no sign-out control here yet.
- **The operation → solution link is binding and permanent** (ruled 2026-07-27): the Operations admin creates that link and offers no way to change it. No re-point affordance may be added — the operation's records, assignments and menu are all written against that solution's model.
- **Two Opens, two planes** (ruled 2026-07-26). **Solutions → Open** calls `openSolution(id)` and enters the Console design scope — authoring needs no data, so a solution with no operations opens fine, and records resolve to the remembered/first operation if one exists. **Operations → Open** leaves Console entirely: `window.open(`${VITE_FLUXUS_RUNTIME_URL}/?operation=<id>`)` launches the Runtime app in a new tab (dev default `http://localhost:5173`). Solutions shows each solution's operation count.
- **Workbench operation** (`currentOperationId`, `solutionOperations`) — which operation's records the design views show. `openSolution(id, operationId?)` resolves it: the argument if it resolves, else the remembered choice (`fluxus:page-builder:workbench-operation:<solutionId>`) if *it* still resolves, else **none**; `null` means none explicitly, and a stale remembered id is deleted. **There is no auto-pick** (M18, ruled 2026-07-31): falling back to the solution's first operation bound the Console to a partition nobody chose, over an unordered server read, so it could rebind between loads. The workbench's side-menu picker switches it, which re-opens the solution and bumps `scopeVersion` so every design view remounts on the new data. Model and pages are unaffected — they are solution-scoped.
- **`pageRuntime`** — `createPageRuntime({ client: sdmClient })`, the injected handle the runtime cluster (and this package's editor validation) reaches the SDM through. Rebuilt alongside `sdmClient` on each open.
- **`currentSession`** (M15) — the signed-in `AuthSession`, or null in the demo posture. Read by `WorkbenchView` so the hosted workbench evaluates expressions with the same `ctx.user` the Runtime app would; the Console itself has no engine of its own (the workbench builds one internally from `sdmClient`).

Components never import these — they reach the SDM only through the FluxScript wiring (expressions in, callback scripts out).

**The demo page is gone (2026-08-05).** `pages/work-orders-demo.json` shipped in this package and the seed script pushed it into an empty database — a `WorkOrderList` wired to the shared SDM in FluxScript, exercising every wiring mechanism. It went with every other prepopulation path: nothing installs a page, so a fresh database has none until one is authored here. (Git history keeps the file if it is ever wanted as sample material.) The behaviour it demonstrated is unchanged — a page shows the records of whichever operation the workbench's picker names, so Console and the Runtime host agree about what exists (one model, many apps, observably). Before M9 it rendered empty here while the workbench showed rows — the plane split leaking into the product.

## Page persistence (persistence.ts)

Pages live on `@fluxus/server` (backend stage 3, 2026-07-16 — the `pages` table, one row per `(solution, path)`; no localStorage, hard cutover like stage 2). **The database is the source of truth** (ruled 2026-07-26): pages are authored here and versioned by `pages.publish`. No repo file installs a page — the `pages/` bootstrap fixture and the seed script that pushed it were both deleted on 2026-08-05, completing a direction the M9 skip-if-present rule had already started (the earlier "deploying pages = deploying files" posture silently overwrote work done in Console). The client snapshots the scope's page set at connect, so `persistence.ts` reads stay synchronous; writes update the snapshot and round-trip in the background, logging loudly on failure.

The `PageDef` shape and `validatePage` live in `@fluxus/page-runtime` (page defs are opaque jsonb to the server, so unlike the SDM config there is no server-side save-time validation). Every `savePage` here runs `pageRuntime.reportPageFindings` — the page-file counterpart of the engine's config-save-time check. Findings never block the save; a page mid-edit may be broken, loudly.

**Where "loudly" actually lands (2026-08-11).** It used to mean the browser's devtools console, which is not where anyone authoring a page is looking. A page in a real database was found naming a GET while declaring no record — legal, but its reads are not logged, which is exactly what the warning had been saying to an empty room since step 3 shipped. The findings now render in the Console's own bottom panel (`PageProblems.tsx`, in the `ConsolePanel` that had stood empty since the prototype), with a count in the panel header and each row opening the page it belongs to.

Two deliberate properties. It validates **every page in the open solution**, not just the one being edited, so a page that drifted before a check existed surfaces without anyone opening it — that is what makes it find the backlog rather than only police new work. And it still **does not block**: saving a broken page mid-edit stays legal, because the panel now makes it impossible to do so unknowingly. Recomputed on render off the client's page snapshot, which is mutated in place, so `shellStore.pagesVersion` is bumped by every `savePage`/`deletePage` to make the write visible to React.

**Publishing does not check anything yet** — `pages.publish` snapshots whatever the draft is, errors and all. Saving a broken page and publishing one are different acts, and only the first has a reason to be permissive; raised 2026-08-11, not settled.

## Editor UI

Bindings render as read-only expression previews; clicking opens the **expression dialog** (`ExpressionDialog.tsx`): a Monaco editor registered with language id `fluxscript` (`fluxscriptLanguage.ts` — Monarch tokenizer mirroring the DSL keyword set; Monaco is bundled locally via `loader.config({ monaco })` + a Vite `?worker` import — the CDN default rendered a bare textarea when unreachable. Cost: the bundle carries the full editor; code-splitting is a floated cleanup). The dialog validates live via the `pageRuntime` handle — expressions with datasource posture (`attributes` banned), callbacks in `'callback'` mode with `callbackData` as an extra root — and blocks Save on errors. Saving empty clears the binding. Richer affordances (jump-to-function, promote-to-function) are the agreed follow-up (design doc, crossover section).

The PageEditor preview column embeds `PageRenderer` with the live (possibly unsaved) slot configs and context schema, passing `debug={import.meta.env.DEV}` for the `context.page` debug strip.

The configuration column carries the two **page-level** sections above the selected slot's: **Page Context** (declared `context.page` keys) and, since 2026-08-10, **Page Access** — a checkbox per role the solution declares, writing `PageDef.access.open`, with a warning while none is ticked, because a published page no role may open is filtered out of the Runtime's snapshot server-side and surfaces there as a missing page. A solution with no declared roles says so instead (RBAC dormant ⇒ open). Like every other page edit these persist immediately; there is no Save button in the editor.

## Planned upgrades (per root ROADMAP)

1. **Expression ↔ function crossover affordances:** jump from an expression into the functions it calls (and back); one-click promote-to-function. Acceptance bar agreed in PAGE_WIRING_DESIGN; where the inline/function line sits is left to evolve from usage.
2. **Manifest shape contracts** — *deferred by ruling (2026-07-11)*: with attributes captured by the standard form rather than mapped from payloads, contracts lost their main consumer; revisit if silent payload mapping ever becomes needed.
3. **App modules:** coarse-grained reusable apps (e.g. calendar scheduler) ship as manifest-bearing components, rewired per SDM through slot config. The pattern is model-agnostic (non-SDM backends can sit behind the wiring), but schema validation and the audit spine exist only with an SDM.
4. **Pages as SDM citizens:** a page file is a declarative definition validated against the model — same species as an entity file. Shape lands with the backend phase (same store, same write path, same audit).
