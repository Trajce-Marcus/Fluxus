# @fluxus/page-builder — Living Spec

Current design truth for the page builder. Updated in the same commit as any behaviour/design change (see root CLAUDE.md). The layout editor has its own full spec: [LAYOUT_EDITOR_SPEC.md](LAYOUT_EDITOR_SPEC.md). The wiring design rationale and rulings live in [PAGE_WIRING_DESIGN.md](PAGE_WIRING_DESIGN.md); the mechanisms it specifies (expression host, callbacks, `services.page`/`services.activities`, `validatePage`, the renderer) live in **`@fluxus/page-runtime`** since the 2026-07-19 extraction — see that package's [SPEC](../../page-runtime/docs/SPEC.md). This package is the Console side: the editor.

## Shape

Two layers under `src/`:

- **`platform-components/shell/`** — the Console shell (industry-console chrome, M16; three columns since M17): `HeaderBar` (breadcrumb + solution switcher + Data picker), `SideNav`, `InnerPanel` (the section's list column), `ContentArea`, and the router. **Two-level IA (CONSOLE_RUNTIME_SPEC §3):** the store's `solutionId` splits the shell into *organisation* mode (Solutions/People/Billing/Integrations/Settings) and *solution* mode (Overview/Operations/Pages/Settings, then the SDM group and Workbench — `SolutionOperationsSection` mounts the scoped `OperationsAdmin`; `SolutionSettingsSection` edits its name over `solutions.update` and holds the delete danger zone, whose server side is a TODO). Both sets come from the **section registry** (`sections.tsx`) — `{ id, label, group?, render, canLeave? }`; the nav, the content area and the hash router all render from it, so adding a Console surface is one entry. `enterSolutionScope`/`exitSolutionScope` toggle the scope; `scopeVersion` keys `shell-body` so opening/switching a solution (or an SDM config save) remounts every solution-scoped view to re-read the fresh snapshot. Hash routes: `#/<section>`, `#/s/<solutionId>/<section>` — the id segment is **percent-encoded**, because solution ids contain slashes (`demo/sdm`) and an unencoded one re-parses as a different solution.
  - **The inner panel** (`InnerPanel.tsx`, M17): the shell owns the *column*, sections fill it. A section renders `<InnerPanel title actions? head? flush?>` anywhere in its tree and it **portals** into the column — the items are the section's own state (an SDM editor lists its *draft*, unsaved renames included), so lifting them into the shell would be a lie about where they live. The portal host is a module-level div created once and moved into whichever slot is mounted, so the target is live from the first render and survives the `scopeVersion` remount. A section with no list renders no `<InnerPanel>` and the column collapses (`:empty` on the host) — Overview, Settings and the Menu editor are plain two-column pages.
  - The tab strip (`TabBar`) and bottom `ConsolePanel` are **page-editor** furniture, owned by `PagesSection`; the store's `openTabs`/`activeTab` mean open pages, nothing else.
- **`platform-components/page-builder/`** — the editor: PageExplorer, PageEditor, ComponentsPanel, the layout editor, `ExpressionDialog.tsx`, `persistence.ts` (the save path). Mounts as a **solution-level** activity. Rendering and validation are imported from `@fluxus/page-runtime` (`PageRenderer`, `componentManifests`, the validators via the `pageRuntime` handle).
- **`platform-components/admin/`** — the organisation-level surfaces over `ConsoleClient`, routed by `AdminView`: **Solutions**, **Operations**, **People** (`PeopleAdmin` — Members placeholder + `ImplementersAdmin`), **Billing** (`BillingAdmin` — the org's read-only plan + placeholder), **Integrations** (placeholder) and **Settings** (`OrganisationAdmin` — the profile form). `Placeholder.tsx` is the shared "not built yet, here is what will live here" card. `SolutionsAdmin` is a **plain list in the main area** — no inner panel (ruled 2026-07-31, twice): name, id, origin, operation count and **Open**, with **New solution** in the header opening a modal (name + id; the id is permanent, so it is only settable there). `OperationsAdmin` takes a `solutionId` and is **no longer an organisation section** (ruled 2026-07-31): it is mounted by `SolutionOperationsSection` inside the open solution, filtered to that solution, with the solution picker dropped from create and the M11 operation view (Overview + Open in Runtime + menu override + role assignments) in the main area. The operation view (M11) is Overview (name, id, linked solution, Open in Runtime) plus the operation-scoped admin sections that used to be separate picker-driven panels: `OperationMenuSection` and `AssignmentsSection` (the standalone `MenuAdmin`/`AssignmentsAdmin` panels and the `admin/menu`/`admin/assignments` tabs are deleted). `OperationMenuSection` carries the M10 **inherit/override posture** (§5 amended): inheriting shows the solution's `default_menu` read-only (`MenuPreview`) with **Override for this operation** (copies it into the editor); overriding shows the composer with **Save override** / **Revert to solution default** (drops the `menu` key — absent means inherit, `[]` means explicitly empty). The item composer itself is the shared `MenuItemsEditor`.
- **`platform-components/sdm-builder/`** — solution-level SDM editor (slice 1): `SdmView` routes the registry ids `record-types|attributes|workflows|roles|menu` to `RecordTypesEditor`/`AttributesEditor`/`WorkflowsEditor`/`RolesEditor`/`MenuEditor` under one model-publish toolbar. Each editor's master list is an `<InnerPanel>` (M17) — record types, attributes, workflows and roles all list in the shell's second column, detail in the main area (a workflow's activities stay nested in the detail; Menu has no list) (M10 — edits the config artifact's `default_menu` over `MenuItemsEditor`; empty menu drops the key; validated at `config.put` like the rest of the config). Each edits a local clone of `sdmClient.config` and persists via `useSolutionConfig.commitConfig` (→ `saveConfig` → `reloadSolution` → remount). A record type's workflow binding is mandatory (the engine resolves `workflow_ref` at save) — the editor offers no "(none)", only a disabled placeholder until one is picked. Workflow/activity/hook (FluxScript) authoring is deferred. **Editing guardrails:** a module-level dirty registry in `useSolutionConfig` (`sdmDirty` + the `useDirty` hook every editor's dirty state mirrors into) backs the registry's `canLeave` guard, which confirms before any navigation away throws an unsaved draft out; `fk_ref` custom fields pick their target record type and display field from the draft (selects, not free text — display field disabled until a target resolves); empty/duplicate ids (record types, workflows, the selected workflow's activities, roles) disable Save and show one `admin-error` line (`idProblems`); and the three destructive removes (record type, workflow, activity) arm on first click ("Really remove?") and fire on the second, disarming on any selection change.

- **`platform-components/workbench/`** — the workbench, hosted (M15, CONSOLE_RUNTIME_SPEC §4). `WorkbenchView` is a thin host: it mounts `<Workbench client user? />` from `@fluxus/sdm` under the `workbench` tab, passing `sdmClient` and `currentSession`. Raw record access, running any activity, CSV import and the schema navigator are implementer work, so they belong on this plane — and the SDM editor two clicks away stops authoring blind. It runs against the **data operation** (below), so the header's Data picker switches its records; a solution with no operations gets a "No data operation" notice instead. Everything record-shaped lives inside the component's own context — this package owns none of it. The workbench brings its own light chrome into the Console's dark shell; a themed workbench waits on the branding config.

The app component library (AppHeader, InventorList, InventorProfile, Map, WorkOrderList and their prop schemas) moved to `@fluxus/page-runtime`; `src/components/index.ts` re-exports it for the `MyComponents` mount API (`src/api.ts` — the original react-in-html mechanism for embedding registered components, and the real entry: index.html loads it and mounts `Shell`; `src/main.tsx` is a dead POC leftover). The palette registries (`sessionComponents.ts`, `componentSchemas.ts`) stay here as separate lists by standing decision (deriving the three registries from the manifest is a floated cleanup, not agreed).

## SDM runtime (Extraction stage 2; repointed at backend stage 2; slimmed at the page-runtime extraction)

`src/sdm-runtime/engine.ts` holds the platform singletons (fork 2: never in React state). `initSdmRuntime()` (kicked off by `api.ts` at module load; every `mount` awaits it) now only runs the auth gate and creates the solution-independent `consoleClient` — the Console **boots into workspace mode** with no solution connected. Opening a solution calls `openSolution(id)`, which assigns the design-scoped singletons; `reloadSolution()` re-runs it after a config save:

- **`consoleClient`** — `ConsoleClient` for the workspace admin surface (solutions/operations CRUD, publish/versions/governance). Created once at boot; solution-independent.
- **`sdmClient`** — `FluxusClient.connectSolution({ solutionId, operationId })` (design plane: config + draft pages by `solutionId`, **records from the chosen operation** — M9) into the engine's `MemoryAdapter`. Reassigned on each `openSolution`; undefined in workspace mode (only solution-level views read it). `saveConfig` persists the SDM config; `publishConfig`/`configVersions`/`rollbackConfig` back the SDM toolbar's Publish/Versions dialogs.
- **Organisation settings** (M14, CONSOLE_RUNTIME_SPEC §1a): `OrganisationAdmin` under the **Settings** section — a Profile form (name, contact email, over `ConsoleClient.putOrgProfile`) plus the org id. The read-only **plan/status/registered** reads under **Billing** since M17 (same `orgs.get` data, the surface a plan belongs on). Plan and status are ours to set, never the org's, so they are display-only; there is no create — signup needs user → org resolution the auth tier does not do. `HeaderBar` shows the org name beside the Fluxus wordmark at **both** IA levels, and the wordmark itself is the way back to the organisation.
- **The operation → solution link is binding and permanent** (ruled 2026-07-27): the Operations admin creates that link and offers no way to change it. No re-point affordance may be added — the operation's records, assignments and menu are all written against that solution's model.
- **Two Opens, two planes** (ruled 2026-07-26). **Solutions → Open** calls `openSolution(id)` and enters the Console design scope — authoring needs no data, so a solution with no operations opens fine, and records resolve to the remembered/first operation if one exists. **Operations → Open** leaves Console entirely: `window.open(`${VITE_FLUXUS_RUNTIME_URL}/?operation=<id>`)` launches the Runtime app in a new tab (dev default `http://localhost:5173`). Solutions shows each solution's operation count.
- **Data operation** (`currentOperationId`, `solutionOperations`) — which operation's records the design views show. `openSolution(id, operationId?)` resolves it: the argument, else the remembered choice (`fluxus:page-builder:data-operation:<solutionId>`), else the solution's first operation, else none. The header's **Data** picker switches it, which re-opens the solution and bumps `scopeVersion` so every design view remounts on the new data. Model and pages are unaffected — they are solution-scoped.
- **`pageRuntime`** — `createPageRuntime({ client: sdmClient })`, the injected handle the runtime cluster (and this package's editor validation) reaches the SDM through. Rebuilt alongside `sdmClient` on each open.
- **`currentSession`** (M15) — the signed-in `AuthSession`, or null in the demo posture. Read by `WorkbenchView` so the hosted workbench evaluates expressions with the same `ctx.user` the Runtime app would; the Console itself has no engine of its own (the workbench builds one internally from `sdmClient`).

Components never import these — they reach the SDM only through the FluxScript wiring (expressions in, callback scripts out).

The demo page (`pages/work-orders-demo`) ships as a bootstrap file — `pages/work-orders-demo.json` in this package — loaded by the seed script into an empty database: a `WorkOrderList` wired to the shared SDM in FluxScript, exercising every wiring mechanism. It shows the records of whichever operation the **Data** picker names, so Console and the Runtime host agree about what exists (one model, many apps, observably). Before M9 it rendered empty here while the workbench showed rows — the plane split leaking into the product.

## Page persistence (persistence.ts)

Pages live on `@fluxus/server` (backend stage 3, 2026-07-16 — the `pages` table, one row per `(solution, path)`; no localStorage, hard cutover like stage 2). **The database is the source of truth** (ruled 2026-07-26): pages are authored here and versioned by `pages.publish`; repo files under this package's `pages/` are a **bootstrap fixture** for an empty database (page path = file path minus extension prefixed `pages/`). The seed script is skip-if-present, so re-seeding never overwrites live edits — the earlier "deploying pages = deploying files" posture is retired, since it silently overwrote work done in Console. The client snapshots the scope's page set at connect, so `persistence.ts` reads stay synchronous; writes update the snapshot and round-trip in the background, logging loudly on failure.

The `PageDef` shape and `validatePage` live in `@fluxus/page-runtime` (page defs are opaque jsonb to the server, so unlike the SDM config there is no server-side save-time validation). Every `savePage` here runs `pageRuntime.reportPageFindings` — the page-file counterpart of the engine's config-save-time check. Findings never block the save; a page mid-edit may be broken, loudly.

## Editor UI

Bindings render as read-only expression previews; clicking opens the **expression dialog** (`ExpressionDialog.tsx`): a Monaco editor registered with language id `fluxscript` (`fluxscriptLanguage.ts` — Monarch tokenizer mirroring the DSL keyword set; Monaco is bundled locally via `loader.config({ monaco })` + a Vite `?worker` import — the CDN default rendered a bare textarea when unreachable. Cost: the bundle carries the full editor; code-splitting is a floated cleanup). The dialog validates live via the `pageRuntime` handle — expressions with datasource posture (`attributes` banned), callbacks in `'callback'` mode with `callbackData` as an extra root — and blocks Save on errors. Saving empty clears the binding. Richer affordances (jump-to-function, promote-to-function) are the agreed follow-up (design doc, crossover section).

The PageEditor preview column embeds `PageRenderer` with the live (possibly unsaved) slot configs and context schema, passing `debug={import.meta.env.DEV}` for the `context.page` debug strip.

## Planned upgrades (per root ROADMAP)

1. **Expression ↔ function crossover affordances:** jump from an expression into the functions it calls (and back); one-click promote-to-function. Acceptance bar agreed in PAGE_WIRING_DESIGN; where the inline/function line sits is left to evolve from usage.
2. **Manifest shape contracts** — *deferred by ruling (2026-07-11)*: with attributes captured by the standard form rather than mapped from payloads, contracts lost their main consumer; revisit if silent payload mapping ever becomes needed.
3. **App modules:** coarse-grained reusable apps (e.g. calendar scheduler) ship as manifest-bearing components, rewired per SDM through slot config. The pattern is model-agnostic (non-SDM backends can sit behind the wiring), but schema validation and the audit spine exist only with an SDM.
4. **Pages as SDM citizens:** a page file is a declarative definition validated against the model — same species as an entity file. Shape lands with the backend phase (same store, same write path, same audit).
